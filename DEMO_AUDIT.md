# Demo-mode audit

Audit date: 2026-10-28. Scope: the `dashboard/` Next.js app and the read-only FastAPI
endpoints it consumes. This file records what existed before any demo-mode code was added.

## Short version

There is **no frontend demo mode today**. The dashboard is already read-only, but every
page fetches a live FastAPI process at request time. A Vercel deployment with no API would
render the "Could not load the run console" error page.

The backend exposes a `GET /api/demo` endpoint returning `{enabled, run_count}`, but the
frontend never calls it. It is metadata, not a data source.

## Every backend call made by the frontend

| Call site | Function | HTTP request | Purpose |
| --- | --- | --- | --- |
| `dashboard/app/page.tsx` | `getStats()` | `GET {API_URL}/api/stats` | Four metric cards |
| `dashboard/app/page.tsx` | `getRuns({limit, offset, status, repo})` | `GET {API_URL}/api/runs?…` | Filtered, paginated run table |
| `dashboard/app/runs/[id]/page.tsx` | `getRun(id)` | `GET {API_URL}/api/runs/{id}` | Full run detail |
| `dashboard/lib/api.ts` | `getDemoInfo()` | `GET {API_URL}/api/demo` | Unused by the frontend |
| `dashboard/app/layout.tsx` | plain anchor | `{NEXT_PUBLIC_API_URL}/docs` | "API docs" header link |

`API_URL` is resolved once in `dashboard/lib/api.ts`:

```text
PRGUARD_API_URL -> NEXT_PUBLIC_API_URL -> http://localhost:8000
```

All requests use `cache: "no-store"`. Both pages declare `export const dynamic =
"force-dynamic"`, so Next.js does not prerender them at build time and will call the API on
every request.

## Environment variables the dashboard currently needs

| Variable | Where | Required? | Notes |
| --- | --- | --- | --- |
| `PRGUARD_API_URL` | server components | live mode | Preferred server-side API base |
| `NEXT_PUBLIC_API_URL` | layout/docs link, browser fallback | live mode | Inlined at build time |
| `PORT` | `next start` / Playwright | no | Local runtime only |
| backend variables (`DATABASE_URL`, GitHub App, provider keys…) | FastAPI | live mode | Never read by the dashboard |

There is no `.env.example` under `dashboard/`, and no documented Vercel configuration.

## What is missing for a zero-backend demo

1. **No static capture.** Nothing exports real runs to JSON. `data/demo.db` and
   `data/demo-comment.md` are generated by `backend/scripts/demo_smoke.py`, but they are
   local SQLite/Markdown artifacts and are gitignored.
2. **No demo flag.** `NEXT_PUBLIC_DEMO_MODE` does not exist anywhere in the repository.
3. **No static loader.** `lib/api.ts` only knows how to `fetch()`.
4. **No banner.** The layout has no indication that data is recorded, and the header always
   links to a live API's `/docs` endpoint.
5. **No provenance.** There is no manifest with capture date, git commit, provider, sandbox
   mode, or run configuration.
6. **No demo tests.** Existing Vitest tests cover the live API client and components.
   Existing Playwright tests start `e2e/mock-api.mjs` on port 4100 and point the app at it.
   The fixtures in that file are hand-written for deterministic UI tests; they are **not**
   genuine run captures.
7. **No Vercel configuration.** The repository has no `vercel.json`, no dashboard
   `.env.example`, and no documented root-directory setting.
8. **No secret scan.** Git history has not been scanned with gitleaks or an equivalent.
9. **No recording instructions.** README embeds dashboard screenshots but has no script or
   reserved location for a 60–120 second recording.
10. **No "real vs demo" section.** README describes the local smoke caveat in two image
    captions, but not as a product-level distinction.

## What already works and should be reused

- **Read-only by design.** `backend/app/api/routes.py` has only GET endpoints. The UI has no
  run-now, upload, delete, or trigger control, so there is nothing to disable in demo mode;
  the banner and a read-only tooltip are still required so a visitor does not assume a
  backend exists.
- **Stable JSON shapes.** `backend/app/schemas.py` defines `RunSummary`, `RunDetail`,
  `RunStats`, `RunList`, and `DemoInfo`. The frontend types in `dashboard/lib/types.ts`
  already mirror them.
- **Genuine local pipeline.** `backend/scripts/demo_smoke.py` runs the real worker,
  `RunProcessor`, LangGraph nodes, npm install, and Vitest against `demo-repo`. It persists
  six steps, one generated test, and sandbox executions into `data/demo.db`.
- **Deterministic UI tests.** `dashboard/e2e/mock-api.mjs` is useful for the existing live-mode
  E2E path and should stay; it must not be presented as captured data.
- **Error and empty states.** `app/page.tsx` already renders an API-unreachable panel, a
  filtered-empty state, and a no-runs state. The detail page maps a 404 to Next.js
  `notFound()`.

## Constraints and caveats that must be visible

The local smoke run is genuine execution, but it is **not** a Docker, live-GitHub, or
live-LLM run:

| Dimension | Capture reality |
| --- | --- |
| Sandbox | `LocalSandboxRunner`; no container, no network isolation, not a security boundary |
| GitHub | Deterministic in-process fake; no App, installation token, webhook, or real comment |
| LLM | `FakeLLM` with one scripted proposal and one scripted review; zero provider calls |
| Repository | `acme/prguard-demo` fixture; no private repository data |
| Cost | FakeLLM reports zero cost; the UI will show `$0.00` |

Docker, a GitHub App installation, and provider keys are not available in this environment.
A live capture can be added later by running the same exporter against a database populated
by the real system; the manifest schema is designed for that.

## Design chosen for the implementation

- `NEXT_PUBLIC_DEMO_MODE=true` switches `lib/api.ts` from `fetch()` to committed JSON under
  `dashboard/public/demo-data/`. No API URL is read in demo mode.
- JSON is imported at build time rather than fetched in the browser. Vercel can therefore
  render the dashboard without a backend, and the data is bundled even if `public/` asset
  serving changes.
- The run list stays server-rendered so URL filters and pagination keep working. No static
  export is required; the deployment is a read-only Next.js app with zero outbound calls.
- The detail route keeps dynamic params. An unknown id renders the existing 404 page.
- The banner is driven by `manifest.json`, not by hard-coded dates or hashes.
- `data/demo.db` stays gitignored; only sanitized JSON is committed.
- The capture script re-runs `demo_smoke.py` by default, then exports through the same
  Pydantic response models the API uses, so the JSON cannot drift from the API shape.
